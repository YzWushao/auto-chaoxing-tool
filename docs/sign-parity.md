# 签到流程对齐说明（v0.6.0）

v0.7.0 已增加签退活动与本人照片流程，详见 [签退与本人照片验证](signout-face.md)，并改为使用原项目模型，详见 [模型来源与 CPU 适配](../models/chaoxing-captcha/README.md)。

交互和协议参考 [aquamarine5/ChaoxingSignFaker](https://github.com/aquamarine5/ChaoxingSignFaker)，实现为浏览器与 Python 后台，不生成 APK。当前按核心签到、验证和扫码流程优先推进，并非宣称所有 Android 功能已经迁移。

## 核心流程

1. 当前用户自己的会话读取课程 / 群聊活动，确认归属及签到类型。
2. 读取 `getPPTActiveInfo` 的活动要求，执行 POST 预签到及 `analysis → analysis2` 确认；不执行响应中的 JavaScript。
3. 预签到明确显示已签到时同步本地成功记录，不重复提交；截止、权限失败等明确报错。
4. 需要滑块验证时使用 ChaoxingSignFaker 原项目 `captcha.ort` 模型推理，CPU 不支持时使用同权重 FP32 兼容版本，最多自动校验两次；低分、模型不可用或平台未接受时，显示手动拼图滑块。v0.6.0 的颜色 / 区域规则已移除。模型来源、原文件哈希及兼容转换脚本随源码公开；**模型预测不等于平台确认通过，也不保证所有验证类型均可自动完成**。
5. 验证通过后，凭据由后台绑定用户及活动，携带 `validate` 与平台提供的 `enc2` 继续签到。仅平台明确成功或已签到才记录完成；`validate_...` 本身不是成功。

验证图片通过限定的 HTTPS 验证图片域名读取，不带用户 Cookies；不使用第三方识别服务。验证 token、iv、enc2 和通过凭据只在内存中保存，最多 180 秒、最多 128 个待处理记录，不写入 SQLite / 日志或导出 JSON。网页只获得临时记录编号和 PNG 图片，不能自行提交伪造的 validate。验证接口要求管理员会话、CSRF、账户归属和活动绑定，并限制操作频率；取消、过期或成功使用后撤销。

## 网页扫码

- 摄像头持续识别与相册图片识别共用用户队列。URL / `SIGNIN:` 格式在普通图片入口、相册队列及 QQ 图片解码中保持一致。
- 相册入口在本地解码，选图后自动为勾选用户签到，可更新同一活动的图片；不需要摄像头权限，HTTP 私网也可以使用。图片是否过期由平台判断，不额外拒绝旧图。
- 实时摄像头仍需 HTTPS / localhost；支持的设备会显示补光灯与变焦。前 / 后置优先在启动前选择，切换镜头先停止后重启。
- 二维码同时需要位置时，可选择当前实际所在的已保存点位，后台重新读取点位并转换坐标；不信任前端任意坐标覆盖保存值。
- 滑块验证及明确要求人工处理的状态不会消耗用户失败次数。完成手动验证后继续读取最新二维码；需要在官方客户端处理的状态可处理后点击“处理后继续重试”。普通失败仍在本轮第 11 次时移到队尾。

## 功能边界

| 功能 | 当前状态 |
| --- | --- |
| 普通、二维码、位置、手势、签到码、已有图片 objectId | 已有流程，现共用预签到与验证处理 |
| 课程 / 超星群聊签到、多用户、QQ 交互 | 已有；群聊仍需设置开启 |
| 动态扫码、相册、滑块验证、验证后继续队列 | v0.6.0 接入；自动识别有手动回退 |
| 二维码附加预设位置、镜头补光 / 变焦 | 已接入；硬件控制依浏览器和设备能力显示 |
| 签退事件、本人照片及官方结果核对 | v0.7.0 接入；人脸最终接受情况依平台，官方活体 / 设备校验仍需官方完成 |
| 普通拍照签到的直接上传、校园定制 App 专用流程 | 尚未完整迁移 |

离线回归覆盖请求顺序、平台拒绝、验证 / 活动绑定、跨用户隔离、伪造凭据拒绝、过期与取消、动态换码与相册队列。公开验证接口仅做无账号的配置和图片读取检查，没有提交真实验证答案、真实签到或人脸数据。最终兼容性与成功率仍需真实活动验证，不能据离线测试声称全功能复刻完成。
